## V0.5.0-alpha.5.1.11 可用于论文的工程案例：从“列表分页”升级为二维 Launcher Layout Schema

真机反馈表明，一维 `App[]` 即使增加分页，也无法表达真实桌面的留白、单 App 独页、Widget 跨格、局部换位等语义。alpha.5.1.11 因此将桌面建模改为 4×6 二维网格，每个 Item 持久化 `(page, x, y, w, h)`；App 为 1×1，小组件为 2×2/4×2。这个案例可以用于说明“UI 看起来像手机”和“数据模型真正支持手机交互”之间的差异。

本轮还形成了两个可写入工程章节的调试案例：第一，左侧 2px 白线最终定位为 `filter: blur()` 装饰光斑在 Chromium compositor 中的裁切缝，说明视觉 artifact 不应只按 scrollbar 猜测；第二，Pointer drag/swipe 必须在 window 级处理 `pointerup/pointercancel/blur`，否则局部 DOM 失去事件后会形成拖拽 ghost 粘滞。

## V0.5.0-alpha.5.1.10 可用于论文的工程案例：从原生滚动分页切换到确定性 Launcher 手势状态机

真实设备反馈发现，单纯隐藏 CSS scrollbar 不能可靠消除浏览器原生滚动指示，同时“固定至少两页”会制造无内容空页。alpha.5.1.10 因此把 Launcher 分页从浏览器 scroll state 改为应用自己的 `currentPage + pointer gesture + transform` 状态机；页面实体由内容自然产生和回收。这一变化可以用于说明 PWA 中“浏览器默认交互”与“OS-like 可控交互”之间的工程取舍。

## V0.5.0-alpha.5.1.9 可用于论文的工程案例：Launcher 展示状态从扁平顺序升级为持久分页模型

真机反馈证明，仅把一维 App 列表按容量临时切片并不能等价于真实手机分页：当用户把 App 拖到第二页时，如果系统只保存 `homeAppKeys[]`，下一次归一化会把它重新挤回第一页，页面本身也无法作为长期状态存在。

本轮把桌面 Presentation State 从 `homeAppKeys[]` 扩展为 `homePageKeys[][] + dockAppKeys[]`。旧数据仍以一维列表兼容读取，首次加载时自动迁移；新模型显式保存“哪个 App 属于哪一页”，并支持空白页、跨页拖动、删除页后的入口合并。该字段继续复用 `appCustomizations` 非索引记录，因此 IndexedDB V18 无需 schema migration。

同时，主屏被定义为固定画布而不是可纵向滚动的普通网页：Phone Shell 外层滚动被锁定，Home Page 自身不生成纵向 scrollbar；编辑菜单作为 overlay 呈现，不通过修改内容 padding 改变布局坐标。这可用于论文说明“移动 OS 心智模型与 Web 页面模型的差异”以及“展示状态迁移的向后兼容策略”。

## V0.5.0-alpha.5.1.8 可用于论文的工程案例：外部开源样本驱动的兼容边界强化

本轮不是复制同类产品功能，而是把 SullyOS·糯米机作为外部工程样本，对“虚拟手机”的 Launcher、角色资产共享、世界书输入兼容、上下文编译、长期记忆与后台 Agent 行为逐层审查，再映射到本项目已有架构。

直接落地的工程改动包括：多页拖拽 Launcher；Character Card Import / Export 双向安全净化；SullyOS-shaped WorldBook adapter regression；Memory confidence / recall feedback 检索评分。它们都建立在现有 GenerationContext、WorldBook Engine V2、Resource Archive、六层 Memory 上，而不是引入第二套平行 Runtime。

论文可把这个过程表述为“reference-informed independent implementation”：外部项目用于发现问题类别与设计边界，实际实现重新基于 Vue / Dexie / 本项目领域模型完成。这样既能说明调研价值，也能清楚区分参考与原创实现。研究来源、许可边界、差异矩阵和后续路线见 `docs/research/SULLYOS_DEEP_STUDY_2026-09-18.md`。

## V0.5.0-alpha.5.1.7 可用于论文的工程案例：玩家可设计 Launcher 与 Presentation State 解耦

本轮从真实手机主屏截图和真实用户反馈中发现：如果把“虚拟手机”主屏压缩成固定六入口功能面板，即使功能逻辑正确，也会破坏用户对手机 Launcher 的既有心智模型。用户预期的是 App 网格、底部 Dock、壁纸、长按编辑态与可选 Widget，而不是在桌面放一段说明文字告诉用户“长按可设置”。

系统因此把桌面布局显式定义为 **Presentation State**：`homeAppKeys / dockAppKeys / homeWidgetKeys / widgetStyle / wallpaper / icon` 统一保存在本地 `appCustomizations`，只决定入口如何呈现，不改变 Character、Conversation、Memory、Social Runtime 等业务事实。隐藏音乐或海龟汤只会隐藏 Launcher 入口，不会删除功能路由、角色数据或运行时状态。

这个案例可以写入“虚拟手机交互模型”“本地优先个性化”和“业务状态 / 展示状态分离”章节。可验证指标包括：

- 从桌面隐藏再恢复某 App 后，该 App 原有业务数据保持不变；
- Dock 最多 4 个入口，布局重启后保持；
- Widget 增删、材质修改与壁纸修改不触发数据库 schema migration；
- alpha.5.1.6 升级到 alpha.5.1.7 时旧 `appCustomizations` 能使用默认布局回填，不清站点数据即可恢复音乐、海龟汤与 Dock；
- Launcher 的个性化不改变聊天 Prompt、Memory 检索或 Social Runtime 候选结果。

设计研究参考 Apple Home Screen customization、Widgetsmith、Color Widgets、ScreenKit，详细记录见 `docs/research/HOME_WIDGET_CUSTOMIZATION_STUDY_2026-09-18.md`。

## V0.5.0-alpha.3.2 可用于论文的工程案例：AI 内容与 Presentation 的职责分离

本轮从真实用户截图中发现典型的生成式 UI 问题：当模型既负责“说什么”又负责“页面长什么样”，独立 App 容易出现 UI 套 UI、视觉风格漂移、Token 浪费与脚本安全风险；但若一刀切禁用 UI，又会破坏 Character Card 社区在聊天中的作者状态栏与 Regex/HTML 生态。

系统因此采用 **Surface-aware Presentation Policy**：Chat 是社区 Presentation 的主要承载面，普通文本由本地气泡承载，作者 UI 进入 SafeRichHtml；朋友圈、音乐、游戏等原生 App 则只允许模型产自然语言或业务数据，界面由 Vue 本地确定性渲染。对于模型误输出的 HTML/XML/CSS，运行时做降级清洗而非执行。

该设计可用于论文中的“生成内容与界面渲染分层”“安全边界”和“多 Surface 一致性”章节。可验证指标包括：

- Native App 中模型 HTML 标签残留数 = 0；
- Chat 中社区作者 UI 的可用率不因 Native App Policy 下降；
- Mixed Rich reply 中普通叙事裸贴背景的比例 = 0；
- Native App Prompt 中重复 HTML/CSS 模板 Token 数接近 0；
- 同一角色跨 Chat / Moments / Music / Game 时，视觉由 Surface 决定、人格由 Character Runtime 决定。

## V0.5.0-alpha.3.1 可用于论文的工程案例：自动 AI 行为的费用边界与 App Surface 隔离

本轮新增朋友圈自主发帖后暴露了一个典型 AI 应用问题：传统定时器只是性能问题，但当定时器会触发付费 LLM 请求时，它同时属于**费用与用户授权边界**。初版默认开启、3 分钟最短间隔、45 秒轮询；稳定化后改为显式 opt-in、前台/在线运行、30 分钟最小间隔，并设置 in-flight guard 防止慢请求重入。

这一案例可写入“系统安全性与资源控制”：AI 自动行为应满足 **用户明确授权 + 可见运行条件 + 频率上限 + 并发上限 + 失败退避**，而不是把普通后台任务模型直接搬到 LLM 调用上。

同时，朋友圈、音乐和海龟汤作为独立 App Surface 通过 service 使用 Provider，而不是继续扩张 `ChatRoom.vue`。路由采用 lazy import，说明系统在增加产品功能时仍保持“App Surface / Runtime / Provider / Persistence”边界。

可验证指标包括：

- 未开启自动朋友圈时后台 LLM 请求数应为 0；
- 任意时刻自动朋友圈并发请求链 ≤ 1；
- App 切到后台时自动发布请求数应为 0；
- 删除全部自建/示例角色后重启，角色数量不应因 seed 被意外恢复；
- GitHub Pages 安装后的 PWA start_url 应保持在仓库 scope 内。


## V0.5.0-alpha.3 可用于论文的工程案例：时间点一致的会话分支与回滚

AI 角色聊天的“回到旧消息重新生成”和“从旧消息创建独立分支”不能只操作可见 Message，因为 Memory、ConversationStateHistory、WorldBook timed state、Prompt Debug、引用关系都可能包含未来剧情。alpha.3 将目标抽象为 **point-in-time replay**：先确定保留消息前缀，再按来源与时间 cutoff 选择可继承派生状态。

其中 rewind 保留用户锚点但删除它旧版本产生的派生状态，随后重新应用当前锚点；branch 则复制节点前的消息和派生数据，并重新映射消息 ID。对没有 sourceMessageId 的数据再使用时间 cutoff，防止“未来状态穿越”。这可以作为论文中**本地优先 AI 会话的分支一致性、派生状态生命周期和可追溯性**案例。

可验证指标：

- 分支后 parent / child 的 Message ID 重合数应为 0；
- 新分支悬挂 reply reference 数应为 0；
- branch 节点后的 automatic Memory / StateHistory 泄漏数应为 0；
- rewind 后旧节点 Prompt Debug 残留数应为 0；
- rewind 后 old thought / active resource / lorebook timed effect 残留数应为 0。

## V0.5.0-alpha.2.1 可用于论文的工程案例：冲突行为合同的回归收敛

alpha.2 已将 149 个自动化用例中的失败从 7 个降到 1 个。最后一个失败不是单纯“代码写错”，而是两个都合理的交互合同发生冲突：一方面，隐藏协议明确给出多个 `text` 时应保留多气泡；另一方面，scene-merged 模式要求 `scene_action + dialogue` 合并成剧情气泡。

最终通过引入“是否存在可见 scene_action”这一运行时条件进行分流，而不是删除任一测试：有可见动作时执行 scene-merged；无可见动作时保留显式多 text 边界。这个案例适合用于论文中的**回归测试、行为合同冲突与最小修复面**说明。

## V0.5.0-alpha.2 可用于论文的工程案例：兼容层回归测试驱动修复

### 背景

V0.5.0-alpha.1 在 Windows 真实环境中 Build 成功，但 149 个自动化用例仍有 7 个失败。项目没有直接删除失败断言，而是先判断“测试语义是否仍代表产品合同”，再区分生产实现缺陷与测试 fixture 缺陷。

### 可写入论文的方法

把兼容层异常分成三类：

1. **资源分类错误**：独立 WorldBook 被误判为角色卡；
2. **表示/序列化兼容错误**：HTML 模板 marker 贪婪、旧 Regex 一层过度转义、字面 `\n`；
3. **运行时语义错误**：明确多 `text` 的消息边界被 scene-merged 抹掉。

其中 World Info Regex 的失败不是运行时错误，而是测试中的三个脚本都使用同一个显示名，导致 `applied: string[]` 断言无法区分来源；因此只修 fixture，不改变运行 API。这一案例可以说明项目采用“测试作为行为合同，但测试本身也需验证有效性”的工程方法。

### 论文价值

这组修复适合放在“系统可靠性与兼容性验证”章节，强调社区角色卡生态存在多种历史序列化差异，兼容策略采用**原数据不改写、失败后窄 fallback、安全渲染**，而不是针对某个角色名/作者名硬编码。

## V0.5.0 可用于论文的工程案例：Conversation Mutation 一致性

### 问题

早期聊天页直接删除 `Message`，但自动记忆、状态历史和消息引用属于同一剧情事实的派生数据。只删 UI 可见消息会出现“用户已经删除某句话，但角色仍通过 Memory / ConversationState 记得它”的不一致。

### 设计

V0.5 引入 Application Runtime 层，将聊天变更建模为 Conversation Mutation：

```text
用户操作
→ Conversation Mutation Runtime
→ Message / Memory / StateHistory / Reply Reference / Conversation metadata
→ 重建当前 ConversationState
```

自动记忆与手工/导入记忆采用不同生命周期：剧情删除只清理由消息自动生成的派生记忆，用户显式维护的长期资料不随普通消息操作消失。

### 可验证指标

- 删除源消息后自动记忆孤儿数；
- 删除源消息后 StateHistory 孤儿数；
- reply quote 悬空引用数；
- Restart 后旧剧情状态残留数；
- 快速切换聊天时最终 route id 与 rendered conversation id 一致率。

### 论文价值

这比“实现删除按钮”更适合写入系统设计章节，因为它体现了本地优先 AI 应用中**可见会话数据与 AI 上下文派生状态必须保持事务一致性**。

## V0.4.4.7 可用于论文的设计素材：角色资源与剧情会话生命周期分离

### 问题来源

社区角色卡通常同时承担“角色设定”和“默认开场”两种职责。若应用把角色卡与唯一聊天记录绑定，用户想重新体验同一角色时只能重复导入角色；从旧消息建立分支时也容易把当前最新状态错误带回旧时间点。另一方面，把“远程/同场”和气泡排版绑定，会使世界事实与 UI 偏好互相污染。

### 设计方案

V0.4.4.7 将系统拆为三个生命周期：

```text
Character / Shared Resources
Conversation / Opening Choice
Branch / State Snapshot
```

- Character 保存长期角色设定与共享资源绑定。
- Conversation 独立选择自由开局或作者 greeting。
- Branch 从指定消息节点复制历史并按 StateHistory 重建节点状态。
- Presence 作为可演化世界状态，在生成前由明确用户移动更新；Presentation 只影响显示。

### 兼容性方法

对社区内容采用“协议分类而不是角色特判”：Action、Dialogue、Author Text Status Header、Community UI 分开解析。针对作者 HTML，Compiler V2 只保存并复用作者静态外壳，动态角色内容仍由真实 AI 生成，从而同时降低 Token 和格式失败率。

### 可验证指标

- 相同 Raw Card 重复导入识别率。
- 自由开局是否完全不写入 first_mes。
- 分支节点之后的状态/资源是否不会回流到新分支。
- 明确场景转移动作 together/remote 识别准确率。
- 结构化括号备注误判 Action 的数量。
- 备忘录/文件引用误判为聊天语句的数量。
- 固定 HTML UI 首次调用成功后是否避免第二次格式纠偏调用。

## 2. 研究背景素材

现有聊天机器人多以通用问答为主，角色身份、情绪、关系和长期经历缺乏持续性。用户在不同会话中可能需要重复说明人物设定，不同角色也容易出现回复口吻趋同、上下文失效和信息串联等问题。

本项目以“虚拟手机”为统一交互载体，将通讯录、私聊、朋友圈、日记、记忆、世界状态和小游戏等功能组织成多个虚拟应用，使 AI 角色不只存在于单一聊天框中，而是形成可持续运行的数字生活空间。

---

## 3. 用户需求与核心问题

### 3.1 角色创建门槛

部分用户能够完整编写人物卡，部分用户只能描述零散想法，还有部分用户暂时没有明确人设。

系统需要同时支持：

- 逐项填写
- 整段人物卡导入
- 模板辅助选择

### 3.2 角色隔离

每个角色需要拥有独立的：

- 身份
- 人设
- 说话方式
- 会话
- 消息
- 情绪
- 关系
- 记忆
- 世界认知

### 3.3 角色一致性

面对相同问题，不同角色应表现出可辨识的语言差异；同一角色在多轮对话中应尽量维持稳定人设。

### 3.4 本地数据安全

角色资料、照片和消息需要持久化保存，并支持后续导出、备份和跨设备迁移。

### 3.5 模型可替换性

系统不能把界面直接绑定某个 AI 厂商，需要通过统一 Provider 接口接入不同模型。

## 4. 总体设计思路

### 4.1 虚拟手机式交互

PhoneFrame 提供统一手机外壳，StatusBar、DockBar 和 HomeScreen 构成 Phone OS。聊天、通讯录和资料页作为独立应用运行。

### 4.2 数据驱动

页面不再通过角色姓名写死跳转，而是使用 UUID、Character ID 和 Conversation ID 建立数据关联。

### 4.3 本地优先

原型阶段使用 Dexie 和 IndexedDB，先验证功能闭环，再增加后端与云同步。

### 4.4 Provider 抽象

页面通过统一 ModelProvider 调用 AI。未来增加真实模型时，保留聊天界面和数据结构。

- `src/components/CharacterAvatar.vue`
- `src/views/ContactsView.vue`
- `src/views/ChatList.vue`
- `src/views/ChatRoom.vue`

**验证结果：**

照片头像在通讯录和聊天中正确显示。

**论文可用章节：**

关键功能设计与实现——多类型头像资源的统一渲染。

### 5.2 点击苏晚却进入顾言聊天

**现象：**

用户在通讯录点击苏晚，聊天标题和内容却属于顾言。

**原因：**

早期演示代码写死：

- 林夏 → `conv-lin`
- 其他角色 → `conv-gu`

**解决方案：**

按以下条件查找会话：

```text
type === 'single'
memberIds.length === 1
memberIds[0] === character.id
```

不存在时自动创建单聊。

**设计意义：**

系统由固定演示数据转为真正的数据驱动。

**论文可用章节：**

数据库设计、角色与会话关联模型。

## 11. V0.0.8 角色生命周期管理补充

### 11.1 角色完整生命周期

系统已从“仅能创建角色”扩展为：

```text
创建 → 查看 → 修改 → 使用 → 删除
```

新增 `CharacterDetailView.vue`、`CharacterEditView.vue` 和 `characterService.ts`。详情页负责展示与操作入口，编辑页负责表单回填、校验和保存，服务层负责角色更新、会话标题同步与安全删除。

**论文可用章节：** 系统总体设计；关键功能设计与实现。

### 11.2 删除角色后的数据一致性

直接删除 Character 会留下孤立会话与消息。当前安全删除在 Dexie 事务中执行：

1. 查找包含该角色的全部会话；
2. 单聊：删除消息和会话；
3. 群聊仍有成员：仅移除该角色；
4. 群聊无成员：删除群聊及消息；
5. 最后删除角色。

**论文可用章节：** 数据库设计、事务处理、级联删除与数据完整性。

### 11.3 角色改名与会话标题同步

角色姓名和单聊标题分别保存在 Character 与 Conversation 中。更新角色时同步修改单聊标题和更新时间，避免聊天列表显示旧名称。

### 11.4 路由冲突与修复

固定路径 `/characters/new` 与动态路径 `/characters/:id` 同时存在。最终按以下顺序组织：

```text
/characters/new
/characters/:id/edit
/characters/:id
```

并删除重复路由。

### 11.5 TypeScript 工程问题

- `characterService.ts is not a module`：服务文件缺少有效导出或未完整保存。
- 类型断言解析错误：将 `gender` 和 `replySpeed` 的类型转换提前到对象外。
- `TS6133`：删除 RouterLink 替代后遗留的未使用函数。

**工程启示：** 每个模块以 `npm run build` 作为最终验收。

## 2026-09-18 · alpha.5.1.12
Launcher Grid V6 已将 App/Widget 统一为二维布局 Item，并推进 Character Card Import Report、WorldBook/Context Inspector、AgentAction capability boundary、Backup Zod preflight 与 HomeLayout Schema。新增的 WorldBook per-entry decision trace 与 Backup restore preflight 可作为“可解释上下文编译”和“破坏性操作前原子校验”的工程案例。


### alpha.5.1.13：动态 Launcher 重排

本轮将主屏编辑从“交换两个图标”升级为“插入 + 流式重排”。拖动中的布局预览与最终持久化分离，周围 App/Widget 会根据目标插入点动态后移；组件尺寸参与同一二维装箱算法。该实现可作为“可预测本地状态机 + 即时交互反馈”的工程案例。


### alpha.5.1.14：临时页面与持久页面分离

Launcher 将“拖到最后一页右边缘时出现的临时空白页”与持久 `HomeLayoutPage` 明确分层。临时页只属于交互预览状态，不进入稳定页集合；拖拽结束后依据持久页面数量夹紧当前页索引。该设计避免 UI 瞬时状态泄漏为长期布局状态，是桌面运行时中“preview state / canonical state”分离的一个具体案例。


### alpha.5.1.15：Launcher 幽灵页自愈

本轮把“空页回收”从单一数组过滤提升为状态机一致性问题：稳定布局、拖拽预览和临时新页三者必须严格隔离。实现上通过 HomeLayout Revision、自愈回写、拖拽 finally 清理和渲染级空页检测，保证 UI 可见页与 IndexedDB canonical layout 最终一致。该案例可作为论文中“本地优先 UI 派生状态与持久状态一致性”的具体工程实例。

### Launcher Folder 与稳定页 GC（alpha.5.1.16）

主屏幕进一步从二维 App/Widget 网格扩展为 `app | widget | folder` 三类统一 HomeLayout Item。文件夹保持 1×1 占位，但内部维护成员 App 列表；因此玩家可通过拖叠两个 App 创建文件夹，再继续追加成员，而不需要单独的“新建文件夹”表单。文件夹成员仍属于桌面 App 集合，避免因聚合显示而丢失数据语义。

空页问题则采用三层一致性策略：Domain normalize 负责清理持久空页，Launcher render 层拒绝展示稳定空页，当前页 DOM 若确认没有任何 Launcher Item 则触发持久自愈。该实现可用于论文说明本地优先 UI 中 canonical state、derived state 与 transient interaction state 的一致性治理。

### Folder Runtime 双向容器（alpha.5.1.17）

文件夹从“只能收纳 App”的单向 UI，升级为可逆的 Launcher 容器：App 可拖入形成文件夹，也可从文件夹直接拖回桌面、跨页或 Dock；容器内部支持插入排序；成员数降为 1 时自动解散。该实现强调“容器只是布局关系，而不是 App 的所有权变化”，因此 App 身份、路由与业务数据不随文件夹操作改变。


### Launcher 幽灵页自愈与可恢复故障处理（alpha.5.1.21）

主屏分页故障表明，仅依赖持久数据 `items.length` 无法覆盖浏览器合成层异常。项目将页面健康检查拆成“数据有效性”和“真实绘制证据”两层，并采用两阶段恢复：优先无损 reflow；如果页面仍视觉空白，则先保存原始 page JSON 到本机恢复槽，再回收 Launcher 页。该方案体现了“故障自愈不等于直接删数据”的本地优先工程原则。

WorldBook Activation Inspector V3 同时记录激活类型、匹配分数、递归深度、估算 token、priority/order/position/probability；Context Inspector V2 记录各来源字符数与近似 token，可用于论文中的“可解释上下文编译器”案例。
